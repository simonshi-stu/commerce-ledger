# Commerce Ledger 面试讲解与自测

本项目是 AI 辅助开发的 Python/FastAPI + SQLite 教学作品集，使用合成数据，没有真实商家上线、支付或生产用户。先自己运行并理解证据，再把掌握的内容写到简历。

## 一分钟项目介绍

“我用一个小型商品、库存与订单场景学习关系数据库和 Python 后端。重点是多商品下单的事务一致性、幂等重试、库存竞争、不可改写的业务历史，以及备份恢复。路由由 FastAPI 承接，Pydantic 验证输入，服务层组织 SQL，SQLite 管理事务和约束。用 67 项自动测试及真实本地 HTTP 演示验证了业务闭环。项目由 AI 协助编写代码和测试，我正在通过逐步运行、追踪 SQL 和解释边界掌握它；没有做过生产部署，也没有验证 PostgreSQL。”

理解以后用自己的话说，不要直接背诵“不熟悉但听起来很强”的术语。

## 业务场景和规则

单商家后台维护商品，手动入库/盘点调整，创建订单后立即扣减可售库存。订单只能从 PLACED 变为 CANCELLED 或 FULFILLED。取消追加返还流水且仅返还一次；FULFILLED 是本地模拟履约确认，不调用快递或支付。

商品改价不改变历史订单单价；下架是 active=0，不删除历史外键。金额使用整数人民币分，客户端不能自行提交总额。多商品订单必须全部有货才提交。

## 架构和表关系

| 层/表 | 作用与关键点 |
|---|---|
| app/main.py | HTTP、鉴权、错误映射、请求编号；调用业务层 |
| app/schemas.py | 严格整数、字段范围、禁止多余字段和重复商品 |
| app/service.py | 下单、状态转换、库存调整、一致性核对 |
| app/db.py | 每次操作独立连接、外键、WAL、事务上下文 |
| products | 商品主数据；SKU 唯一，价格为分，active 表示上架状态 |
| inventory | product_id 既是主键又是外键，保存当前可售数量 |
| orders | 订单主记录；request_key 唯一，存请求摘要、状态和总额 |
| order_items | (order_id,product_id) 联合主键，保存数量及当时单价 |
| stock_movements | ADJUST/SALE/CANCEL 流水；(product_id,kind,reference) 唯一 |

products:inventory 为 1:1；orders:order_items 为 1:N；products 同时被明细和流水引用。inventory 是便于读写的当前值，流水是业务变动历史，所以需要核对两者；它们不是两份随意重复的数据。

## 沿一次下单解释事务、并发、幂等

1. Pydantic 验证 request_key 和 items，拒绝空单、重复商品和错误整数类型。
2. 服务对商品项排序并计算摘要，因此相同商品换顺序仍是同一业务请求。
3. `BEGIN IMMEDIATE` 获取 SQLite 写事务，再查幂等键；已存在且摘要相同返回已有订单，不再次扣货；不同请求返回 409。
4. 插入订单，逐项检查商品状态，执行 `UPDATE inventory SET available=available-? WHERE product_id=? AND available>=?`，以更新行数判断是否成功。
5. 从服务端商品表取价格，记录明细快照、SALE 流水和总额。全部成功才 commit；任一项失败 rollback，前面已扣的库存也回滚。

SQLite 当前是数据库文件级单写者；BEGIN IMMEDIATE 与条件更新共同保证本地实现的正确性，不能宣传为行锁或高吞吐架构。忙时返回 503/Retry-After，建议保留原幂等键重试；幂等不等同于分布式系统“绝对只执行一次”。

取消在同一事务检查状态、返还库存、追加 CANCEL 流水并更新状态。重复取消返回已有状态；取消和履约竞争只允许一个终态。数据库触发器还限制终态逆转、改写明细和流水，但有架构管理权限的人仍可删除触发器，不能称为防篡改账本。

## 技术取舍与恢复

| 取舍 | 为什么这样做 | 代价/局限 |
|---|---|---|
| SQLite + 原生 SQL | 零数据库服务依赖，能直接看懂约束、条件更新和事务 | 单写者，无 PostgreSQL 行锁/连接池实测 |
| 整数分 | 避免用浮点金额计算 | 没有多币种、税费、折扣分摊 |
| 显式幂等键 + 摘要 | 应对请求超时后重试，拒绝键复用冲突 | 管理凭据是单商家范围；不是多租户设计 |
| 价格快照与下架 | 保留订单历史语义 | 没有退款、退货及商品版本审计 |
| 手动迁移、先备份 | 保留旧数据，不在启动时静默升级 | 要求操作者停写，未自动隔离外部写者 |
| 独立恢复文件 | 验证以后再决定使用哪份库，拒绝覆盖 | 没有自动切换或备份后数据合并 |

备份不是事务替代品。备份使用 SQLite backup API，处理 WAL 中已提交数据；暂存库经结构、外键和业务核对后才发布。备份以后发生的取消不会出现在恢复库中。迁移失败可以回滚 SQL，但不能用“回滚”概念替代文件丢失后的恢复。

## 常见追问，先自己回答再看提示

**为什么不能先 SELECT 库存再直接 UPDATE？** 查询结果可能被别的事务改变；要解释实际隔离/锁语义，并用条件更新验证余额。当前还用 SQLite 写事务串行化，不要声称单靠 Python if 防并发。

**扣完第一件商品，第二件没库存怎么办？** 同一个事务内抛业务异常，rollback 撤销订单、第一件扣减、明细和流水；用失败测试证明。

**服务器已提交，但客户端没收到响应怎么办？** 使用原 request_key 重试，摘要相同返回已有订单；提交后的响应故障测试验证库存只扣一次。换新键会被视为新业务请求。

**幂等键相同但商品数量变了怎么办？** 409，不默默复用旧结果或创建新单；由客户端显式发起新的业务请求。

**库存和流水不一致时为什么不自动修？** 不知道哪一边代表真实业务，自动覆盖可能掩盖错误；先报告异常，核实原因后制定修复事务。

**为什么使用只读快照？** 对账中的多个查询应看到一致状态；否则中间有订单提交可能产生误判。备份验证则在私有、无写者文件上完成。

**索引怎么考虑？** 唯一 SKU/request_key 支持查找和冲突控制，(created_at,id) 支持订单排序，(product_id,id) 支持流水顺序查询。尚未做大数据量基准或 EXPLAIN 性能报告，不编造提升百分比；当前 offset 分页也不是海量数据最佳方案。

**怎么迁到 PostgreSQL？** 需要替换连接与占位符、主键返回方式、PRAGMA/触发器 SQL，设计迁移和连接池，并在真实实例测试并发/隔离/重试；不能仅替换连接字符串。当前尚未完成。

**如何上线？** 目前没有做。下一阶段需要受支持 Python、依赖升级验收、TLS/凭据管理、权限隔离、监控与恢复策略、PostgreSQL 适配和负载测试。不要说“可直接生产使用”。

**AI 做了什么，你做了什么？** 如实说明 AI 协助生成和修改代码、测试、教程；自己实际完成过什么运行、排错、解释和修改就说什么。没有亲自完成的部分不写成独立研发经历。能独立解释代码比背诵项目介绍更重要。

## 30 分钟学习路线

前 5 分钟运行 scripts.demo 和 scripts.recovery_demo，观察库存与订单状态。接着 10 分钟沿 main→schemas→service.place_order→db.transaction 阅读一次下单。再用 10 分钟运行指定回滚/并发/恢复测试，并预测 SQL 改动会怎样破坏约束。最后 5 分钟不用文档解释一次超时重试和恢复流程。

练习只在临时库或独立副本做：改商品价格后查旧订单单价；同键换数量观察 409；两商品订单让后一件无库存验证前一件没有被扣；用恢复演示说明为什么备份后取消会丢失。能预测结果并找到证据，再把项目写进简历。
