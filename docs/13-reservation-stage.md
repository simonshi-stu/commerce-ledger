# 阶段一：库存预留、模拟付款和超时释放

本阶段针对同一商品的库存争抢，使用合成数据与 SQLite。原有直接下单 API 保持现状；新增路径只支持单品、模拟付款，不接平台或真实资金，也不在服务里自动开定时任务。

| 操作 | 路径 | 库存与订单结果 |
|---|---|---|
| 预留 | POST /reservations | 按当前价格建立 HELD 预留，条件扣可售库存；同键同参重放不重复扣减 |
| 查看 | GET /reservations/{id} | 返回状态、期限、数量和价格，PAID 状态返回正式订单 ID |
| 模拟付款 | POST /reservations/{id}/simulated-payment | 截止前相符金额转正式订单，库存不再扣；重复事件返回原凭据；逾期记录 LATE_PAYMENT，不恢复订单 |
| 到期回收 | POST /reservations/expire?limit=50 | 同一事务内查找到期 HELD、归还库存并写流水；最多 100 条，可分批调用 |
| 对账 | GET /integrity | 核对可售库存与流水、订单金额与明细；已验证预留至恢复各阶段余额 |

截止时刻按服务端时间戳判定：同一秒达到 expires_at 就视作过期。过期释放由管理方主动触发，逾期付款也会顺带释放该笔仍 HELD 的库存；读取状态不会修改数据。已付款进入原有订单流程，可继续履约或操作订单取消。模拟迟到的付款需要人工核对；系统不执行退款。已有 SQLite 数据库需要通过 python -m app.migrate --apply 备份升级到 v3。

## 云端合成验证

分别用 50 和 100 个同时出发的线程直接调用预留服务，每轮初始 20 件、每次请求 1 件。

| 总并发服务调用 | 成功预留 | 库存不足 | 超卖 | 超时回收后库存 |
|---|---:|---:|---:|---:|
| 50 | 20 | 30 | 0 | 20 |
| 100 | 20 | 80 | 0 | 20 |

两组库存流水对账无差异。测试还覆盖同一支付事件并发重复、按预留价格扣款、错误金额拒绝、到期边界、迟到支付、重复扫单、预留订单的重复取消、只读权限及旧库迁移。并发测试是服务层正确性验证，不能推断 HTTP 压测的响应时间、跨进程吞吐或 PostgreSQL 表现。本轮不统计线上延迟或真实业务量。

运行测试：python -m pytest -q ；只跑本阶段：python -m pytest -q tests/test_reservations.py 。
