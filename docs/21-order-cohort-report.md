# 订单业务汇总：不把订单金额当成真实收入

## 发现的问题

原先有订单列表、库存和一致性核对，但缺少便于运营直接查看的区间汇总。直接把 orders 和 order_items 联表后 SUM(total_cents)，会把多商品订单的整单金额重复统计；直接合计所有订单，又会把取消单混在有效订单里。

## 新增方案

提供只读 CLI：按订单创建日期筛选，输出当前状态下的订单数量与订单金额，支持 JSON / CSV。订单表逐单统计，不用明细连接扩增订单行，幂等重试不会生成第二笔订单。使用同一只读快照，不写库、不迁移；金额用整数人民币分。

```bash
python -m app.order_report --database data/commerce.db --start 2026-11-01 --end 2026-12-01
python -m app.order_report --database data/commerce.db --start 2026-11-01 --end 2026-12-01 --format csv
python -m scripts.order_report_demo
```

日期为 UTC，开始包含、结束不包含。CSV 可复制导入 Excel。JSON 同时包含非取消订单金额及统计时间。缺少数据库时失败，不会偷偷建立空数据库。

## 可复现业务结果

演示输入为三个模拟订单，每单两件商品，价格分别为 10 和 20 元；每个下单请求再重试一次。分别保留待履约、设为已履约和取消。

结果：只有 3 个订单，待履约、已履约、取消各 1 单 / 30 元；非取消订单金额 60 元。不能说实际营收 60 元，更不能将全部订单 90 元当作收入。若错误地与两行订单明细连接再汇总整单金额，会得到 180 元；本实现避免此口径错误。这是合成场景的正确性证据，不是实际销售提升。

## 边界与后续

这是“某段创建日期的订单，到现在处于什么状态”，不是历史某天营业额，也不是期间取消额。现有数据没有支付事实或履约/取消发生时间，无法推导现金收入、退款、利润或任意过去时点的状态。取消发生后重跑原创建期间报表，数字会改变。后续如要真实运营日结，需要增加状态事件时间和支付/退款流水，不能用 created_at 代替。

本次没有修改 HTTP API 或数据库结构，没有提供 PostgreSQL 支持、生产容量结论或支付接入。
