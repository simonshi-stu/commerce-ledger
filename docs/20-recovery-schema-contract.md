# 恢复时也要保护下一次写入

## 本阶段完成什么

2026-11-11 基于现有草稿 PR #1 的 `2e48f9f69f399879034f5268aa465db56aec2c80` 开发，46 个基线文件与该远端提交逐一比对一致。没有合并主分支、部署服务或连接真实订单。

发现的问题：在合成数据库删除 `stock_movements_delete_guard` 后，数据库仍标记为 v2，SQLite 结构检查、外键检查和当前库存对账也正常。旧版 verify 和 backup 因此都返回 `verified: true`，但恢复文件已不能阻止删除历史流水。

原因是这些检查回答的问题不同：

- `user_version=2` 只是版本标记，不能证明 v2 的迁移内容仍完整。
- SQLite `integrity_check` 验证文件内部结构和现有约束，不能知道应用要求存在什么触发器。
- 当前数据对账正确，不等于下一次写入仍受保护。

## 修复路径

1. 使用当前发布源码中的受信任迁移，在独立内存数据库构建参考结构。
2. 从参考库及待验证库读取 `type / name / tbl_name / sql`，按类型和名称排序比较。
3. 检查应用表、索引、触发器以及未知应用对象。SQLite 自有的 `sqlite_*` 对象不纳入比较，例如 ANALYZE 产生的统计表。
4. 结构有差异时返回 `VerificationError`，不自动修复原库。backup 和 restore 在私有暂存文件验证失败后清理暂存目录，不发布目标文件。
5. 原有 SQLite 完整性、外键、库存、订单金额和 SALE/CANCEL 关联检查仍执行。

参考结构只由仓库迁移生成，不执行待验证文件提供的 SQL。缓存仅存在于当前进程。SQL 保持逐字比较，不通过删除空格或小写转换去假装两个表达式相同，避免改变引号内的字面量含义。

## 限制与下一步

- 这是当前应用发布版本的严格结构合同。自行添加索引、表、视图、触发器，或只改 DDL 的格式，也可能被拒绝，即使人工认为语义等价。请保留原库，先在独立副本审查差异，再通过明确的迁移和测试支持该结构，不要为了通过验证直接删除对象。
- SQLite 内部统计等对象不做结构合同验证；该功能不是任意外来数据库文件的安全沙箱、来源认证或防篡改签名。
- 对活动数据库直接 verify 仍是诊断用途：结构和业务核对使用不同的只读快照。backup / restore 验证的是无并发写入的私有暂存文件。
- 本轮没有实测 Windows、真实 PostgreSQL、生产灾备、跨主机故障和断电持久性。此前 PostgreSQL 候选仍未纳入此 SQLite 分支。
- GitHub CI 是否执行以对应提交的远端检查为准，本地全绿不能替代远端 CI。当前未新增工作流。

## 面试讲解

可以解释：“备份可恢复至少涉及文件可读、关系约束、当前业务对账和未来写入规则四层。这次我通过删除历史保护触发器复现误判，再增加参考迁移的结构合同，并测试失败时不覆盖原数据、不发布半成品。”

也要说明取舍：严格比较容易推理，代价是拒绝自定义或等价重写的结构；这是学习原型中的安全默认值，不是通用数据库迁移识别器。代码经 AI 辅助实现和审查，实际能力以可重复测试与上述边界为准。
